# Reproduction notes: arXiv 2608.05819

Differences found between the paper and the authors' release (`alfred-miquel/LTR-Quantum-Contraction-Plans`
at `936630a`). "Paper" means the arXiv text; "code" means the release. We report what the code and data give;
we can't tell from them why they differ from the text. Numbers: `results/t06_t07.csv` and
`results/t06_t07_composition.csv`, regenerated by `experiments/t06_t07.py`.

## Phase 1: ranker on the published splits

**Reproduced exactly: Table 6, Top-1, Top-3, Regret1, Regret3 of both models**, in Python and with the
authors' Julia code (`experiments/julia/t06_t07.jl`), under these conditions, all from their Notebook 5:

| The paper says or implies | The code does |
|---|---|
| One model per row | Two models per row: `opt_ndcg` takes Top-1 and Regret1 from 1 round, Top-3 and Regret3 from 65; `opt_pair` from 16 and 14 |
| `opt_ndcg`: eta 0.01, subsample 0.7 (Table 4) | eta 0.02, subsample 0.8; Table 4's values never give the published Top-3 or regrets in rounds 1–300 |
| Regret on speedup, `1 - Sp_1 / Sp*` | Regret on the label, `log(1 + Sp)`. On speedup, no round matches, and MinFill's Regret1 is 0.1015, not 0.0735 |
| Labels `log(1 + Sp)` | Yes, natural log, then converted to integer ranks within each circuit before training |

No single model at any round from 1 to 300 gives all four published values in a row. The release doesn't show how the
round counts were chosen.

**One model per objective, rounds from grouped 5-fold CV on the training split alone**, over three fold
assignments and both `opt_ndcg` parameter sets:

| | Top-1 | Top-3 | Regret1 | Regret3 | Win | Paper's row |
|---|---|---|---|---|---|---|
| `opt_ndcg`, ID | 56–60 | 88–92 | 0.021–0.023 | 0.0008–0.0037 | 80 | 60 / 96 / 0.0141 / 0.0004 / 92 |
| `opt_pair`, ID | 44–60 | 68–88 | 0.021–0.032 | 0.0021–0.0076 | 82–86 | 60 / 92 / 0.0211 / 0.0004 / 88 |
| `opt_ndcg`, OOD | 27–34 | 47–55 | 0.044–0.104 | 0.019–0.024 | 72–83 | 38.71 / 62.90 / 0.0520 / 0.0181 / 73.39 |
| `opt_pair`, OOD | 24–27 | 45–58 | 0.085–0.103 | 0.020–0.027 | 63–69 | 30.65 / 62.90 / 0.0800 / 0.0234 / 87.10 |

Regrets here are on labels, to compare with the paper. The ID comparison with MinFill (Top-1 12%) holds up. On OOD
the Top-3 is close to choosing at random (52.2%, exact expectation on these splits). With 25 ID circuits one circuit is
4 points, and the chosen round count varied from 7 to 158 with the fold assignment, so these are ranges and not point estimates.

**Not reproduced**

- **Table 7.** No code for it in the release. On the training split alone, no round gives `opt_ndcg`'s values.
  Trained on train + ID, some rounds do jointly match Top-1 + Regret1 and Top-3 + Regret3 for `opt_ndcg` (11; 23, 24,
  135–138). For `opt_pair`, Top-1 + Regret1 match at round 54 on train + ID and Top-3 + Regret3 at round 14 on train
  alone. This suggests Table 7 is composed like Table 6, but it isn't established.
- **Win rate**, with our reading of it (plan ranked first against MinFill, ties half). No code in the release.
  `opt_ndcg` ID stays at 80–84 where the paper has 92.
- **The random and MinFill+random baselines.** No code in the release. Exact expectations on the published splits
  are random 16.13 / 46.40 / 0.0798 / 0.0204 / 56.95 against the paper's 22.95 / 58.44 / 0.0699 / 0.0137 / 70.16,
  and MinFill+random Top-3 44.93 against 28. MinFill's own Top-1 and Regret1 (12%, 0.0735) do match.
- **`mf_ndcg` baseline.** Not attempted.

**The stored models are not test evidence.** `models/opt_pair.json` is the Notebook 5 recipe fitted on all 225
circuits, ID and OOD included: predictions agree to under 1e-5 at 1850 rounds. `opt_ndcg.json` looks similar (Top-3
100% on OOD) but we didn't identify its exact parameters. The authors' README calls these production models, for which
that's a normal choice. They score far above the tables (Top-1 84–97%) for this reason, and Table 6 doesn't use them.
They rank well on the z-scored split features and poorly on raw ones (ID Top-1 8–16%), while their Notebook 4 passes raw values.

**Data**

- The split files cover 225 circuits, as the paper says, in 1475 rows. Features are standardised, not as in
  `Features.xlsx`; a z-score over the training rows doesn't recover them, so the scaler is unknown (for phase 2).
- `RQC_3_7_40` and `RQC_3_7_52` have plans listed twice in the training split (12 duplicated rows), with the same features but
  speedups differing by up to 0.84. They count as one group of 14 and one of 11.
- Three training circuits have no MinFill plan (`RANDOM_11`, `RQC_5_32`, `pricingcall_nativegates_ibm_qiskit_opt3_25`), though speedup is defined against it.
- `measures.xlsx` holds speedups against MinFill only (1367 rows), no raw times and no second GPU. It lacks 97 rows
  of the splits, and differs from them in 155 rows (up to 727.9, in QFT circuits). We use the split files.

**Library version matters.** xgboost 2.1.4 in Python matches their Julia stack (XGBoost_jll 2.1.5) to about 5e-8 in
predictions. xgboost 3.4.1 gives different models from the same inputs (differences of 0.03–1.06), so the project pins 2.1.4.

## Phase 2: plans, features, scaler, networks

Numbers: `results/p2_plans.csv`, `p2_scaler.csv`, `p2_split_sources.csv`, `p2_networks.csv`, regenerated by
`experiments/p2_plans_features.py`; checks in `tests/test_plans.py`. Line numbers refer to the release at `936630a`.

**Plan files.** The release's `plans.tar.gz` holds 1663 files. 1661 parse and are reproduced byte for byte when
written back (`qctn.plans.authors`). Two have a truncated line and don't parse: `Qwalk_5` (line 1009, the two tensor
names are missing) and `RANDOM_11_pla_mf` (line 71, three names and a rank are missing). With the release's reader
(`read_contractions_analisi_ranks_indexs`, `src/Funcions_de_Features_v_5.jl`) these lines would also fail, at the
integer parse. Two further files reuse a result name, so they aren't a valid tree: `QWALK_3_pla_Flow_cutter` (step 75)
and `QWALK_6_pla_flow_cutter` (step 1451); neither generator name is one of the seven. Four plans (`RQC_4_20_*`,
`RQC_4_60_*`) end with four disconnected roots. The line format is `print(f, ...)` in `contract_pair_rank!`
(`src/funcions_article_IA.jl`, l. 183) followed by the `@timed` seconds of a mock contraction (l. 41, 48): the last
column is a time, not a cost.

**Features: matched.** `qctn.features` reimplements `get_features_v5` (`src/Funcions_de_Features_v_5.jl`,
l. 341–394); Notebook 2 (`2_Getting_18_features_from_file.ipynb`, cell 8) calls it on each file. On the 1657 plans
that are both parsed and in `Features.xlsx`, 1651 agree on all 18 features to 1e-9 relative (in practice to rounding),
and the QFT_5 values printed in Notebook 2, cell 12, are reproduced to 1e-12. The constants and choices, all from
the code:

| | The paper states | The code does |
|---|---|---|
| ε in d_i | ε ≪ 1 (Eq. 9, App. A.3), no value | `epsilon=1.0e-6` (l. 29, 56) |
| τ in frac_tiny | "e.g. τ = 6" (App. A.6, Eq. 26) | `tau=6` (l. 131), steps with c_i ≤ c_max − 6 |
| q in topq_mean_cost | I_q = the ⌈qS⌉ largest c_i (App. A.5, Eq. 22), no value | `q=5` percent, k = `max(1, round(Int, S*q/100))` (l. 116–119): rounding to nearest (ties to even), not ceiling; the two differ on 781 of 1661 plans |
| std_cost | std(c_i) (Eq. 24) | `Statistics.std`, sample std (ddof = 1) |
| w_i | 2^(c_i − c_max) / Σ 2^(c_ℓ − c_max) (Eq. 11) | 2^(c_i) / Σ 2^(c_ℓ), the same ratio; largest c_i in the release is 394, so no overflow |
| k_i | \|S_i\| | (r_A + r_B − r_C) / 2 from the file's ranks (l. 548–549); equals the printed index count on every step |

**Features: not matched.** Six plan files give other features than their `Features.xlsx` rows, and the step counts
differ (file vs xlsx): `RQC_4_11_pla_mf` (1 vs 168), `RQC_4_20_pla_fc`, `_gn`, `_mf` (189, 189, 192 vs 263),
`RQC_4_60_pla_fc`, `_mf` (189 vs 698). The `RQC_4_20` and `RQC_4_60` files have the same step sequence and contain
outer products (45 steps with no common index, results up to rank 43). For such a step the release's reader indexes
`comptador[0]` (l. 582), which is out of bounds in Julia; we haven't run it. `Features.xlsx` must come from other
versions of these files. `RANDOM_11_pla_mf` has an xlsx row but its file doesn't parse.

**The split files' scaler: identified up to the row set.** In each split file only the 13 model features are
standardised; the other five columns are raw. With the raw values from `Features.xlsx`, each standardised column
is one affine map of the raw value, the same for both objectives and all three splits, residual ≤ 1e-14
(`results/p2_scaler.csv`; `max_asym_val` 1.6e-8, its σ is 1.5e-7). So it's a z-score with fixed μ, σ per feature.
For the integer features (`n_steps`, `max_out_rank`, `max_red_rank_val`), μ·N and the sum of squares
σ²(N − 1) + Nμ² are integers only for N = 773 (or multiples) with ddof = 1: the scaler was fitted on 773 rows, with
the sample std (so not sklearn's `StandardScaler`, which uses ddof = 0). We didn't find which 773 rows. Tried, none
reproduce μ and σ (best: training rows, μ off by up to 0.016 σ, σ off by up to 6.6%): all 1658 xlsx rows; the 1561
rows of the seven generators; the 1475 split rows, as published, deduplicated, or replaced by their own xlsx rows;
train, train + ID, train + OOD, ID, OOD alone; circuits with exactly seven plans; rows present in `measures.xlsx`;
speedup ≤ 2; ddof 0 and 1 for each. An exact-cover search over whole circuits (scipy `milp`, 60 s per pool) didn't
terminate. The release contains no scaling code (no z-score, `StandardScaler` or normalisation in `src/` or the
notebooks), and the paper mentions none (Sec. 5.3 says features are fed to XGBoost).

**Jdrasil rows in the splits carry MinFill's features.** Of the 224 `_pla_jdrasil` rows in the split files, 213 have
exactly the features of the same circuit's `_pla_mf` plan, where `Features.xlsx` (and our recomputation from the
plan files) gives the Jdrasil plan different features. Their speedups are their own (e.g. `GHZ_100`: Jdrasil 1.027,
MinFill 1.000, same features). For 7 rows Jdrasil and MinFill have equal features anyway; 4 rows match neither.
In all, 13 split rows match no xlsx row: the 4 rows of `RQC_4_6_34`, the 7 of `RQC_6_20`, `RANDOM_10_pla_jdrasil`
and `RQC_5_28_pla_jdrasil` (`p2_split_sources.csv`). The other 1249 rows equal their own xlsx row. In those 213 circuits the ranker sees two plans with identical features and
different labels.

**Circuits and networks: matched where they can be compared.** Only 17 of the 332 circuit names in the plan files
have a QASM file in the release (`dj_*`, `portfolioqaoa_*`, `pricingcall_*`; 15 of them in the splits). The others
(GHZ_n, RQC_*, QFT_*, QNN_* …) are named differently from the 257 QASM files or were built in Julia (Notebook 1_a
uses `create_ghz_circuit`), and we haven't mapped them. `qctn.circuits.authors_gates` follows `import_from_qasm` and
`process_gate_line!` (`src/funcions_qasm.jl`, l. 113, 608–821) and `qctn.tn.build` follows QXTools `convert_to_tnc`
with QXTns `push!` (gate tensors in circuit order, two-qubit gates split by SVD, then inputs, then outputs). Replaying
all 109 plans of the 17 circuits on our networks reproduces every step's three ranks and the common indices' qubit
tags, prime levels and dimensions (ITensors' random index ids can't be compared). Conventions found on the way:

- QXZoo's `GateCall2(symbol, ctrl, target)` stores its first qubit as `ctrl`, while `c_x(q_target, q_ctrl)` passes the
  target first; with the authors' `c_x(target, ctrl)` the network gets the qubits in QASM order (control first).
  `swap` and their `cu1` end up in reversed QASM order. This only affects which half of the gate gets the lower id.
- The authors' parser only reads gates on a register named `q` and skips other lines with a printed message
  (l. 821). Over the 257 QASM files it drops 38,397 `cp` and 8 `x` on the Grover `flag` register (the release has
  `replace_qasm_registers_grover` for those, l. 516, which we haven't applied) and every `u` (179), `u3` (130),
  `ccx` (68) and `cry` (12). None of these occur in the 17 compared circuits.
- QXTns `push!` (`tensor_network_circuit.jl`, l. 97) reshapes `A` instead of `B` when the SVD rank is 1, so the second
  half gets the first half's data. Ranks and ids are unaffected.

A Julia dump of the network (QXTools via PyCall) for an independent check hung at package loading on the login node
and was dropped; the replay against the plan files is the check.
