III · Seven techniques

The paper's pipeline: generate seven plans, then rank them

For each circuit: candidate plans \(P_1,\dots,P_7\), runtimes \(T(P_i)\); learn a score \(f(\phi(P_i))\) whose order matches the runtimes — the fastest plan should come first. Label \( y_i=\log\big(1+T(P_{\text{MinFill}})/T(P_i)\big) \).
arXiv 2608.05819 (Pastor, Castillo, Badia, Aug 2026). 225 circuit groups from MQTBench and QXTools in 11 families (Table 10); seven candidate plans per circuit (Sec 5.1): MinFill and FlowCutter via QXTools, a Girvan–Newman heuristic, the Jdrasil heuristic, the Tamaki local-improvement heuristic and two MinFill-based PACE 2017 entries (Jégou–Kanso–Terrioux). Each plan runs 50 times on an RTX A6000 (Julia, OMEinsum.jl, CUDA, Float32); the label is y = log(1 + speedup over the MinFill plan) (Eq. 12–13). Features: 18 plan-level features from the GEMM shape of each step, 13 per selected model (Table 2). Ranker: XGBoost with rank:ndcg or rank:pairwise, validated on NDCG@3. This act puts the seven on one map before the deep dives.
III · Seven techniques

Seven candidates on one map: which graph, which direction

One column per click, bottom-up first because the elimination game is fresh. Rows: which graph the method works on. MinFill, FlowCutter and the solvers order the indices (index graph = line graph of the tensor graph), so their output is an elimination order or tree decomposition that must be converted into a pairwise plan; Girvan–Newman cuts the tensor graph and its dendrogram is already a pairwise plan. Columns: bottom-up = decide the first contraction first; top-down = decide the last cut first; search = spend time improving a decomposition. The classification is ours; the paper lists the seven (Sec 5.1) without a taxonomy. Seven = 3 + 1 + 1 + 2.

None of the four optimizes GPU runtime. Only the solvers target width directly; the other three optimize proxies that often, but not always, correlate with it. This is the gap the learned ranker fills: generate structurally different plans, then pick using features of the plan itself.

\[ \text{runtime} \neq f(\width): \quad \text{runtime} = F\big(\{(m_i, n_i, k_i)\}_i,\ \text{hardware}\big) \] "Plans with similar theoretical complexity may perform very differently" (arXiv 2608.05819, abstract).
Our own measurement, not the paper's: 200 MinFill plans for the talk's circuit, differing only in tie-breaking (data/S21.json). 193 of them have the same max intermediate rank 8, but the bars — the GEMM work exponent c_i of each step in execution order — are arranged differently: total cost differs by 2^0.75 ≈ 1.7× in FLOPs, the share of tiny steps and the shape imbalance differ too. The paper gives no table of equal-width runtimes; it states the point qualitatively (abstract; Sec 3.2; App. A.1 "Why width alone is not sufficient"; App. A.7 "runtime is not a monotone function of FLOPs"). That is the case for ranking a diverse pool instead of trusting one score.
